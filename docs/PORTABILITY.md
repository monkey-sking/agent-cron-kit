# 从私有环境搬到公开仓库，会踩的坑

这些都是真出过事的，不是假想。

## 1. `{{SECRET_xxx}}` 出了宿主就变成字面量

私有环境里，配置可以写 `TOKEN="{{SECRET_xxxx}}"`，由调度器在运行前解密替换。
把这段代码原样复制到别人的机器上，`0f727c207f70` 就是一个普通字符串 ——
程序会拿着它去认证，服务端返回 401，然后（如果脚本写得"优雅"）静默降级。

**正确做法**：仓库里一律用 `${ENV_VAR}`，并在 `.env.example` 列出变量名。
迁移时把秘密注入到环境，而不是注入到源码。

## 2. 静默语义很美，但失败不能也静默

「正常时零输出」是这个仓库所有任务的约定。它的问题在于：
**空输出和崩溃看起来一样。**

真实事故：一个清理脚本在 launchd 下 `exit 1`，且没有任何 stdout/stderr，
宿主内手跑 `rc=0`。结果连续几周没人知道它根本没执行。

规则：
- 正常 → 零输出；
- 失败 → 必须 stderr + 非零退出码，最好再落一个 outbox 文件；
- 调度器层要记录 `exitCode`，别只记录「有没有输出」。

## 3. 命令里的空格会拆参数

`command` 通常是整串交给 `/bin/bash -lc` 执行的。写成：

```bash
wrapper --title 【Git 自动推送（每日）】 -- bash job.sh
```

bash 按空格切开，wrapper 收到 `自动推送（每日）】` 当成要执行的命令，报
`FileNotFoundError: '自动推送（每日）】'`。三个任务同时挂掉，排查了半天。

**规则**：参数值含空格或全角括号，一律加单引号；改完用
`bash -lc "<完整命令>"` 手动跑一遍，别只看状态文件里的旧 exit code。

## 4. 模型/密钥漂移会静默跳过任务

Agent 类定时任务如果没显式固定 provider + model，全局模型一变，调度器可能直接
跳过执行（防止意外扣费），而且**不报错**——连挂几天零产出才发现。

同理，`launchctl setenv` 设的 key 不跨重启；重启后所有依赖它的调用方会静默降级。
凡是「注入密钥」的脚本，都要配一个可达性探针。

## 5. 峰值与并发

同一份数据被两个进程同时处理会产出重复结果（真实事故：同一天产出了两条重复记录）。
共享出去的脚本如果带「扫描 → 处理」两步，请假设它会被并发执行：
**入口处加原子锁**（`mkdir` 或 `O_EXCL`），别依赖调用方自觉。

## 6. 备份脚本最容易变成新的隐患

备份 = 把敏感数据复制一份。备份脚本进了公开仓库，等于给出「怎么打包登录态」的教程；
备份产物如果顺手放进了仓库目录，等于把数据也公开了。

规则：备份脚本私有；备份目录永远在 `.gitignore` 里；备份体积要有阈值告警
（真实事故：漏排一个 2.7G 的可再生模型文件，每份包 2.4G，磁盘直接被吃满）。

## 7. launchd 与 cron 的差异

- launchd 的环境极简（没有你 shell 里的 PATH / 代理变量），脚本里别假设 `pnpm`、`node` 在 PATH；
- `StartCalendarInterval` 遇到系统睡眠会补跑一次，而 cron 会直接跳过；
- 同一个任务同时挂在 cron 表和 LaunchAgent 上时会**跑两遍**——迁移期最容易犯，
  本项目就曾同时存在两套（59 条 cron + 28 条 launchd，其中大部分是镜像）。
